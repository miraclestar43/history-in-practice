## P1-1 固定每周人工批准改变了长期运行目标

**位置**：`docs/PLAN.md:128–134,140,195,337`；`docs/EDITORIAL_BRIEF.md:77,81`；`prompts/02_OPUS_IMPLEMENT.md:30`。

v2.1 把每周 20–40 分钟人工批准设为永久必经步骤，且事件 ID 的产生依赖它。用户的目标是短时间阅读、让机器人长期每日产出；没有提出每周必须承担编辑工作。这是新增产品负担，不是由“关闭工具的写作调用”必然推出的约束。20–40 分钟也还没有测量依据。

**最小修订**：

- 在启动阶段校准四篇样稿、来源规则及接受标准；长期默认侦察、去重、证据提取、起草与规则检查自动进行。
- 为已纳入来源策略、证据明确且通过检查的候选建立自动准入流程，记录每个通过/拒绝原因。模型自评分数不能代替证据支持。
- 新来源类型、材料冲突、身份/事件不确定、无法支撑的核心细节进入待处理队列；先选其他合格候选或备用稿。只有这些异常需要人工介入。
- 每周人工抽查或策划可作为可选模式；若试运行证明某类必须人工校核，报告实测劳动量和可靠性限制，再调整服务承诺，不能把未接受的固定劳动隐藏进默认设计。
- Python fetcher 可以由模型生成候选检索词/URL，再经来源策略、HTTP 取回和正文校验；必要时另测允许检索工具的研究调用，写作调用仍保持无工具。现有 adapter 无检索能力不等于 Hermes 整体永远不能研究。无需为了这项修订立即搭复杂 agent 系统。

**验收**：自动完成至少连续两轮四类供稿 dry run；无人工点击也能进入合格写作队列；异常进入待处理但不停止其他合格稿；报告每篇实际人工介入时间与原因。不能将这八篇等同于已证明全年无需维护。

## P1-2 空 cwd 没有证明 Hermes 一次性调用已隔离全部上下文

**位置**：`docs/PLAN.md:35,219`；`docs/reviews/FABLE_REVIEW.md:38,86–90`；`prompts/02_OPUS_IMPLEMENT.md:23`。

help 说明 `-z` 默认加载什么，不足以证明该已安装版本如何落实 `--ignore-rules`。上游公开 issue #26633 报告过 `hermes -z --ignore-rules` 在一次性执行路径中未正确转交隔离参数，仍注入全局上下文。该报告不能证明 Pi 所装版本一定受影响，但足以要求核对实际安装源码/行为。空 cwd 只能减少工作目录文件影响，不能排除 Hermes home 中的 SOUL、memory、profile、预加载技能等上下文。

**最小修订**：将“空目录 + flags 已解决隔离”改为待验证要求。记录安装版本及对应代码 revision，检查 oneshot 路径是否传入相应隔离开关，并在可控测试配置中验证。不要改动用户真实 SOUL、memory 或全局配置，也不要直接升级生产 Hermes 来完成新项目验证。

**验收**：测试夹具分别放置工作目录与全局测试上下文的不同 canary；优先检查实际构建的上下文/loader 调用，确认无注入。仅观察模型没复述 canary 不足以证明未加载。确认工具集合为空、一次性调用不读项目/用户记忆，并验证模型报错的退出码与 stdout。若版本确有缺陷，提供隔离的项目级运行方式或明确受控修复，不影响现有 gateway/news 任务。

**上游依据**：[NousResearch/hermes-agent #26633](https://github.com/NousResearch/hermes-agent/issues/26633)。这是一份上游缺陷报告，不能当作本机复现结论；最新 main 文档也不能替代已安装版本的验证。

## P1-3 事件粒度与中文召回尚不能支撑去重承诺

**位置**：`docs/PLAN.md:140–142`；`docs/EDITORIAL_BRIEF.md:77`。

两处规则存在漏判/误判：

1. 同一个宏观 QID 可能覆盖战争、远征或长期运动，其中可有多篇不同事件；不同 QID、重定向或缺失 QID 也可能对应同一故事。“QID 相同即重复”粒度过粗。“人物 + 年份 + 地点”也可能把同一年同一城市的两个不同决定合并。
2. FTS5 不指定中文处理不能保证召回。默认 unicode61 对连续中文不按词切分；改成 trigram 仍不能用 MATCH 检索只有两个字的人名。

**本轮实际复现**：当前环境 SQLite 3.53.1，索引正文 `汉王将黄金交给陈平，授权他实施反间计`：

| 查询 | unicode61 MATCH | trigram MATCH |
|---|---:|---:|
| 陈平 | 0 | 0 |
| 反间计 | 0 | 1 |

同一正文使用 `instr(body, '陈平') > 0` 能找到。此复现只证明相关默认行为，未测试 Pi 的 SQLite 构建。

**最小修订**：

- 项目内部建立不可变 episode ID，表示具体片段/决策；QID 为可选外部关联，增加 `parent_event`，分清宏观事件和单篇片段。
- 内部 ID 由持久注册表分配；编号方式不承担“已查重”的语义。通过规范描述、相关人物、时间精度、地点、行为/决策、来源位置及候选比对识别重复；不用模型 slug 或人手每周命名当作唯一保护。
- 规范化繁简、人名中英别名；对两个字的人名提供结构化实体或子串召回。正文可选中文分词/字 n-gram；FTS5 只作候选召回，最终判断具体片段。QID 重定向需规范化。
- 把已发布、已预备、已排期的稿件都纳入查重；并发准备要有数据库唯一约束/预留，避免尚未发布的双份候选。

**验收**：同事件换标题、语言、繁简、别名、类别及 QID 缺失/重定向均能检出；同一远征 QID 下两个不同片段不会直接误拒；同人物同年同地不同决定可区分；准备中及排期中重复同样被拒；从 Git 重建索引仍得相同结论。

**依据**：[SQLite FTS5](https://www.sqlite.org/fts5.html)、[Wikidata redirects](https://www.wikidata.org/wiki/Help:Redirects)。后者说明 QID 合并/重定向的机制；事件粒度建议是本轮设计判断。

## P1-4 “可取回”与“足以支持四类文章”尚未连起来

**位置**：`docs/PLAN.md:55–60,128–132,156–159`；`prompts/02_OPUS_IMPLEMENT.md:25`。

PLAN §2.4 将英文 Wikisource 相关请求列为未验证，§4 与 Opus prompt 却将 zh/en Wikisource 一并称为已从 Pi 验证可达。更重要的是，当前已证实的组合主要是中文原典正文、导航页和实体数据；导航与 QID 在本计划中不作史实证据，尚不能证明四类题材都可持续获得有不同来源基础的材料。

**最小修订**：按实际 adapter/端点记录 `unverified / reachable / extractable / evidence_usable`，以正文和具体章节为依据，不做整个域名的笼统保证。四篇样稿先各自完成一份真实证据包，列出独立来源基础或诚实披露共同源头。来源政策允许维持低成本的取回机制，并可逐步扩展可靠机构/研究材料；不能把“白名单”理解为永远只能使用少数现有站点。

**验收**：四个类别均展示取回正文、定位、摘录与 claim 支撑；中文原典两站镜像不能算两份独立依据；200 challenge/首页、404 错 URL、可访问但无相关内容分别被识别。依赖缺失不得用模型记忆补齐。

## P1-5 两个“真实可选方案”的硬门槛会诱导编造

**位置**：`docs/EDITORIAL_BRIEF.md:27–35`；`docs/reviews/FABLE_REVIEW.md:200–204`。

要求每个历史主角都曾面对至少两个“当时都说得通的选项”，再否决所有无个人决策点的制度/过程题材，会使题材长期集中于领导者决策，也可能诱导模型替人物编造内心和选项。寻乌提纲中的“写文件还是先问清情况”目前仅是未核实的设计表述，不能先设为史实再去找证据填空。

**最小修订**：保留叙事骨架，但允许以有记录的矛盾、约束、行动、变化与后果组织故事。只有材料支持时才归因人物动机或列出其真实考虑过的选项。作者提出的替代选择、反事实与现代讨论要明确标记，放入分析/开放问题。制度史、科学史或普通人的经历可以以具体事件切入，不因缺乏个人二选一而自动淘汰。

**验收**：四篇样稿逐一标记叙事实证与编辑解释；替代选项不会写成有记录的真实想法。至少用一篇无英雄式决策的事件提纲验证该规则能通过，无需为了验证专门编造情节。

## P2：调整后一起落实的三项

### A. 将篇幅作为试稿区间，而不是已验证的阅读速度

`docs/PLAN.md:83–105` 的区间可用于样稿试验；不应以“旧稿 underfill”强制增加字数。按其中假定的中文 350 字/分，以 1,600 字、900 英文词、1 分钟思考计算：英文 220 词/分共 9.66 分钟；180 词/分为 10.57 分钟；150 词/分为 11.57 分钟。区间上沿在 220 词/分时也约 10.69 分钟。均为计算，不是读者实测。

保留候选长度，允许以真实阅读时间缩短；故事不必为了九个栏目凑字数。简短应用可以和开放问题结合，避免重复讲道理。引用列表与延伸阅读不应算入核心故事时长，但阅读时间标签要说明口径。

### B. 一次 400 字调用只提供起始预算，不证明长文吞吐

`docs/PLAN.md:202–211` 的 600–900 秒及整篇 45 分钟可作为可配置初值。启动、输入长度、推理、输出语言与 provider 波动都会影响 wall time，不能由一次短中文调用得到稳定的英文生成速度。20,000 字符是否不足也应测量真实双语 JSON，不能先断定不足。

至少记录两篇代表性长文的各步耗时、输入 UTF-8 字节、输出字节/字符与重试；补上运行中 stdout/stderr 上限、进程组超时回收，不能只在 subprocess 完成后检查输出大小。多篇库存补充任务采用分篇/分批截止时间；若 service 超时仍设成单篇 45 分钟，会把初始库存构建或恢复补稿在第一篇后杀掉。前夜备稿与库存下限优先于卡死具体性能数字。

### C. 部署核验也应覆盖正文内容

`docs/PLAN.md:214,263` 中的 JSON 校验方向正确，正式链接仍需首次部署确认。`edition_id`、`revision` 与标题相同并不独立证明正文完整；用预期正式对象与线上对象比较，或增加规范化 `content_sha256`，覆盖两个语言、问题、解答和来源字段。取回当天 JSON 后还要实际验证浏览器中两种语言的正文与深链。不能把 JSON 取回成功视为阅读页面已验证。

90 KB 邮件 HTML 上限可保留为工程初值；不要把变化页脚当作保证 Gmail 不折叠的机制。长度与客户端呈现以真实邮件测量为准。
