## 1. P1：复审结果缺少严格 schema，真实问题可能不进入待解决清单

位置：`src/history_in_practice/editor.py:89–108,112–125,172–181,233–256`，`prompts/review_zh.md`；同样检查 pipeline 的初审结果处理。

Caller 接受可解析 JSON，但没有核对 review/parity 的必需字段和类型。reviews 随后自行加入 `_content_sha256`。collect_issues 只消费 `issues` 中的 fix/block，而 prompt 同时允许 `unsupported_claims`、`invented_inner_life`、`quote_mismatches` 三个独立数组。

**实际最小复现**：

1. `issues=[]`，但 `unsupported_claims=["assertion absent from evidence"]`，collect_issues 返回空数组。
2. 模型返回 `{}`，加入本地 hash 后成为非空对象；两个 reviewer 对象的 truthiness 满足当前 final_reviewed 条件，collect_issues 仍为空。由此缺失合法审核结果也可能被视作无剩余问题。

hash 绑定只能证明关联到哪个文本，不能证明返回对象完成了审查。

**最小修复**：

- 对 drafting、review、parity、edit 分别严格校验 schema；至少 review/parity 的 `issues` 必须存在且为 list，条目 severity/path/problem 等类型合法。缺字段或类型错误是模型输出失败，不能视作 clean。
- 三个事实问题数组要纳入统一问题清单；或修改 prompt 只使用一个具类型的 issues schema，并拒绝仍含未转换事实问题的返回。不能只删掉字段来隐藏问题。
- 在 final record 中记录 reviewer 的有效 schema/版本、内容与证据 hash；对实际有效 review 作准入判断，不以 dict 是否非空作为依据。
- 对旧 record 做兼容性标记：旧稿是否已有显式规范 issues、独立事实问题数组是否非空；不要因补字段就把旧记录悄悄变成有效 clean review。

**回归**：`{}`、缺 issues、issues=null、issues 为字符串、未知 severity、只有 unsupported_claims、只有 quote_mismatches、只有 invented_inner_life 均不能准入；合法空 issues 且无其他事实发现可以通过。pipeline、editor 和手工 record 路径行为一致。

## 2. P2：轮询跨过发送截止后，仍可能继续发信

位置：`publish.py:149–157,189–206`。

wait_live 在 sleep 前检查 deadline；sleep 和 fetch 结束后不再检查。最后一次取回成功即可返回 ok，publish_today 进入 SMTP 前也没有新检查。

**复现**：10:59:30 第一次 verify 返回旧版本 → sleep 60 秒 → 11:00:30 新版本成功，wait_live 返回 ok=True。虽然已经过 11:00，当前调用仍可能发信。这与文档“截止后绝不迟发”不一致。

**修复**：sleep 不超过剩余窗口，取回结束后重新判定，进入每次实际发送/重试前再次确认截止。明确 SMTP 已开始但跨过截止如何记录，不能把已接受邮件标成未发，也不能盲重发。

**回归**：sleep 跨截止、fetch 跨截止、临界时间返回成功、两收件人之间跨截止；deadline 后不新发，已开始发送的结果据实际记录。

## 3. 报告中的库存算术需要纠正

当前 0 天覆盖正确：下一类 ancient 无合格稿。

STABILIZATION_REPORT §5 的情景计算有两处错误：

- 现有 world1，加上五个全部批准的样稿 A1/W1/M2/U1，为 A1/W2/M2/U1。从 A 开始可连续排 **4 天**，不是报告写的 2 天；之后缺第二篇 A。
- 报告举例 A3/W4/M3/U3，从 A 开始可排 **12 天**，不是约 10 天。

这两个数字是对所给计数的计算，不表示样稿已获用户批准，也不代表待审稿最终一定能入库。报告、生成表和实际 inventory CLI 应使用同一计算入口，避免手写情景值。

## 4. 第 6 节的建议选择

### 4.1 最终编辑：选 Pi Claude，不继续靠同一 MiMo 增加循环

建议 MiMo 保留为候选、初稿与第一轮检查；有界修订失败后交给 Pi Claude/Opus 作为具名最终编辑。当前用户已有这个 Pi 工作环境，先验证这条现有路径，不新增付费模型账号或采购依赖。

最终编辑必须读取最终全文和原始证据，按段覆盖事实、归属、时序、因果、引语及英语对应，而不是仅修最后一次 MiMo 列的几个点。产出一个稳定的问题清单，逐项修复或有证据地驳回，绑定最终正文/证据/编辑身份和版本。

MiMo 的新 review 不是不可争议的最终裁判。若某条被证据明确推翻，Pi Claude 可以记录引用和理由后关闭；真实事实错误、证据缺失、关键误译依旧阻止入库。不能给整篇一个笼统 exception 来凑库存。主观文风建议与事实错误分级，但不能把事实问题降为 note。

模型编辑同样可能遗漏。保留来源可追溯、可更正机制和抽查，不把“具名编辑”宣称为历史事实零错误保证。

**验证**：先用一篇 ancient 和一篇 modern，清楚记录 MiMo 输入结果、Pi Claude 最终编辑、每项 disposition、最终哈希、耗时和是否入库。不改阈值，不写“同模型零 issue = 客观正确”。能在预算内获得两篇可读合格成稿后再扩到剩余待审。

### 4.2 样稿：读者反馈与内容准入分开

建议用户先读 D 或 B 的中英文各一篇，反馈节奏、趣味与英文；无需要求一次读完五篇才能继续开发。

样稿仍需内容审核，用户“读起来不错”不代替史实核验，也不等于五篇全部批准。可以让 Pi Claude 逐篇完成最终编辑，再保留实际读者反馈；若 owner 决定批准某篇，approval reason 写真实过程，不伪称两位读者都读过。

### 4.3 近现代中国：保留范围，正常转给另一个可用编辑

不因为 MiMo 的提供商限制默认缩窄栏目题材。记录拒绝并停止对同一次拒绝重复改写试探；对正常历史内容，转给已经可用的 Pi Claude 正常起草/审阅，以相同来源与事实标准验收。记录每阶段实际模型身份。

同一个有限调用中断不能丢弃整份证据。按阶段恢复，避免已完成的中文、证据被重复生成。若可用编辑也无法完成，就保留 pending，不能跳过审核。

### 4.4 邮件和网站：可并行做准备，不启动生产发送

用户注册 Resend、验证 read.starhub.vip、私下配置发送 key 与真实可接收的 Reply-To；用明确的 send-test 入口验证 Gmail/QQ、布局和回复路径。凭据不进 Git/模型材料。

Cloudflare 类型、生产分支与构建发布路径通过现有项目设置确认；代码可先整理为可审阅的网站 patch/PR，不因此把未核实的生产部署当作完成。不自行更改 DNS、根域邮件记录或既有网站部署。

### 4.5 定时器

保持关闭，直到：上述两项定点修复通过；最终编辑路径有真实合格交付；四类连续覆盖至少 7 天；两位收件人真实测试及网站部署检查通过；发送时间与截止规则明确。此后先短期受监测运行，不把 73 测试等同于已证明长期运行。
