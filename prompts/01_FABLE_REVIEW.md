# 给 Claude Fable：计划评审与修订

你正在处理 https://github.com/miraclestar43/history-in-practice 。当前阶段是评审计划，后续将由 ChatGPT 再评审，再交给 Opus 实施。

先读取仓库 `README.md`、`docs/PLAN.md` 和 `docs/EDITORIAL_BRIEF.md`。以当前文件和用户需求为准，不沿用尚未核实的旧假设。

## 产品目标

每天约十分钟读一篇有趣、可靠的历史故事，中文与英文参照。四类连续轮换：中国古代、世界史（排除中国和美国）、中国近现代（包含毛泽东相关历史）、美国史。故事可以延伸到有文献依据的现代事件。

用户喜欢小约翰可汗的内容带来的历史兴趣。请检验计划能否形成具体、易读、有人物选择和事实细节的叙事，而不是百科摘要或空泛鸡汤。建立自己的栏目语言，不照搬创作者表达。

每篇在故事之后提供：简短现实应用、适用边界、一个开放问题、一个标为“参考思路”的示例解答，以及可追溯来源和带说明的延伸阅读链接。邮件中文全文在前、英文全文在后；网站默认中文，以 tab 切换英文。

长期目标是每日新内容。已发布正文在 GitHub 归档，也在 StarHub 阅读；同一事件改标题不算新故事。需要持续选题、检查历史归档、提前审核和保持备用库存。内容质量优先，不能凭空编造细节来维持不断更。

## 需要你做的事

1. 独立评审内容设计和技术方案，按 P0/P1/P2 写具体 findings，给出文件位置、影响、最小修复办法与验收方式。不要只说“建议增加质量控制”。
2. 对照仓库核实 news-intel 的 Hermes adapter、website_test 的网站结构；若本机能访问 Pi，再做不输出秘密的只读环境检查。无法访问就明确写未验证，不推测运行已成功。
3. 特别检查：Hermes 当前调用关闭工具，无法自行检索；长文写作需要新入口，不能假设旧 compose 已实现。模型自审不能取代证据。
4. 检查长期内容供给是否现实：每日四类轮换、事件级永久去重、主题多样性、跨语言去重、库存补充、GitHub 持久归档、故障恢复之后避免重发。不要靠向量数据库或无界 agent 链掩盖产品问题。
5. 检查十分钟是否容得下双语正文、开放问题与示例；评估邮件排版、客户端裁剪、网页语言切换与延伸阅读体验。
6. 检查网站部署是否真的配置了 Git 自动部署。现阶段不要改线上 Cloudflare 或 DNS。SMTP、准确收件人和投递时间等缺失输入，集中写出；不要猜邮箱，不读取或公开凭据。
7. 对必要修改直接修订计划，保留核心目标，删除重复与不必要复杂度。明确“已核实”和“建议方案”。

## 交付与范围

- 交付 `docs/reviews/FABLE_REVIEW.md`，包括总体结论、按优先级 findings、已修复项、剩余问题和实施顺序。
- 更新 `docs/PLAN.md`；必要时同步 `docs/EDITORIAL_BRIEF.md`、README 及后续 Opus prompt，避免互相矛盾。
- 将评审范围内的文档改动推到一个短期分支并开 draft PR，给出分支、commit 和 PR URL，供 ChatGPT 再评审。
- 当前不要实现服务、生成充作已审核的批量文章、安装定时任务、修改 news-intel 生产实例、部署网站或向任何人发邮件。
- 可以提出四篇样稿的具体写作提纲来检验设计，但必须标注其事实还需怎样核实，不把提纲视为可发布稿。
- 只有确实阻塞后续实施的问题才问用户；能从代码、配置模板或只读检查确认的，先自己查。Fable 无法做的环境验证，写成 Opus 的具体任务。

最终简明报告：结论、最重要的 3–5 个问题、已改什么、哪些仍未验证，以及供下一轮审查的链接。
